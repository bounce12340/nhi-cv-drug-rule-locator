# TC-20260810-29:規則逐字查詢——條文所提代碼之主檔藥品辨識區塊

- 派發方:Claude Fable 5(dispatcher/acceptor)
- 建置者:Codex GPT-5.6 Sol,reasoning effort **xhigh**(RDL-010)
- 治理依據:RA 2026-08-10 指示(逐字)「那邊的2.6.1,裡面的成分名稱、藥品名稱、健保代碼,這個能否直接呈現方式如同藥品查詢出來的資訊一樣?⋯⋯這樣子很難辨識是哪一個藥品,能否用同一套健保資料庫來呈現?」及後續補充「我希望完全以主檔補上完整資訊,不需要把藥品給付規定表二的全部內容列出,我這邊會進行手動確認。」
- 基準:`main` = `f97f6ab`(TC-28 已合併);測試基準 **307 passed / 34 files**
- 授權基礎:RDL-016(規則資料集 display-only)、RDL-022(藥品主檔系列 display-only);跨資料集嚴格分區並呈之先例為 TC-17 §2.6 與 G1/TC-21

## 0. 問題陳述(派發方已查證)

規則資料集單元 `2.6.1-001` 為約 5,266 字之自由文字,其中嵌有原官方 PDF 之表二藥品表格,但於轉錄時已被**壓平為單欄行序**,且藥品名稱之換行續行落在健保代碼之後:

```
<藥品名稱 前半>
<健保代碼>
<藥品名稱 後半>
```

使用者因此無法辨識條文所列為何藥品。**該資料集雜湊鎖定且經 `INTAKE-APPROVE` 入庫(RDL-015),不得修改。**

派發方實測:2.6.1 條文含 **116 個相異健保代碼**,於藥品主檔 `nhi-drug-items-2026-08-07-r2` 中 **116/116 全部命中**(零查無);2.6.2 含 4 個、2.6.3 含 10 個。詳見 §9。

## 1. 做法:偵測代碼 → 主檔補上辨識資訊

於規則逐字查詢結果中,新增一個**明確標示來源的區塊**,列出該次結果之條文中出現的健保代碼,並以**主檔資料**呈現其藥品辨識資訊。

### 1.1 代碼偵測

- 以**不變量 1 之樣式 `^[A-Z0-9]{10}$`** 之等價字界比對自 `verbatimText` 取出代碼(第二字元允許為數字,如 `A0` 開頭之合法代碼);**不得推測、不得模糊比對、不得自動更正**。**嚴禁自行收窄為僅允許前兩碼為字母之樣式**——派發方曾因此漏檢兩個合法代碼(見 §8)
- 去重並保留條文中之出現順序
- **不得嘗試重組表格結構**——不得由行序推斷「哪個名稱屬於哪個代碼」。此為本單之核心禁令:今日規律一致不代表所有列皆然,一旦推錯即產生「藥名配錯代碼」,於臨床工具屬最嚴重之錯誤類型且無機制可發現

### 1.2 每個代碼顯示之欄位(以 RA「辨識」需求為度)

自主檔取:**中文品名、英文品名、成分、規格量與單位、劑型**。

RA 已明示「我這邊會進行手動確認」,故本區塊之目的是**辨識**而非完整重現:**不納入**價格、價格沿革、給付規定章節、公告異動等欄位——藥品查詢分頁已提供該等資訊。

若某代碼於主檔查無:**顯示固定之查無文字,不得省略該代碼、不得以條文文字填補**。

## 2. 嚴格分區(不得違反)

- 逐字條文**完整保留、逐字不動、不得隱藏或摺疊任何段落**。RA 之「不需要列出表二全部內容」經派發方理解為「不必重組該表格」,**非**「隱藏官方條文」;隱藏官方逐字內容不在本單授權範圍
- 新區塊須自帶**主檔資料集版本識別**與**主檔警語**(`DRUG_ITEM_MASTER_WARNING`,逐字不改),與規則資料集之版本與警語各自標示
- **不得宣稱條文所載藥品名稱與主檔品名為同一值**,不得以主檔品名取代或「更正」條文文字。兩者可能因轉錄時點與來源不同而相異——如實並呈,由使用者自行判讀
- 區塊標題須使使用者明白:此為「條文中出現之代碼在主檔的記錄」,而非條文本身的一部分

## 3. 範圍與禁止事項(違反即 BLOCKED)

- 不得修改 `data/governed/**`、`packages/domain/src/generated/**`、`scripts/**`、`apps/api/**`、`.github/**`
- 不得改動 `packages/domain` 既有查詢函式語意;如需新增,僅可加**純函式**(零 I/O、frozen、有測試)
- 既有測試零修改(基準 307);如遇衝突**停止並回報**
- 不得執行任何 git 指令
- 中英雙語同步;zh/en 字典鍵集合維持相等(TC-22 守護)
- 不得出現 eligibility 黑名單詞彙(中英皆適用)
- 官方逐字內容與 RA 核定警語維持 TC-22 三不翻紅線(位元組一致)

## 5. 驗收標準

1. 五項檢查全綠;測試數 307 + 新增(新增數載明)
2. 代碼偵測正負向測試:精確樣式命中;**近似字串(如 9 碼、11 碼、小寫、含連字號)不得命中**;去重與順序保留
3. **負向測試釘死「不得由行序推斷名稱與代碼之對應」**:helper 之回傳與原始碼皆不得含條文中之藥品名稱欄位
4. 主檔查無之代碼顯示固定文字且不被省略(以合成代碼測試)
5. 逐字條文於新增區塊後**位元組一致**(守護測試)
6. 分區測試:新區塊之版本與警語為主檔者,與規則資料集之版本警語各自呈現
7. bundle 驗證:區塊標題與收合控制字樣在(中英);eligibility 黑名單 0
8. 自我檢查報告:檔案變更、測試數增減、bundle 增量、效能考量、§2 分區之落實說明

## 8. 派發前補充事實(2026-08-10,派發方實測)

- 2.6.1 條文之相異代碼實為 **116**(先前所述 114 係派發方誤用過窄樣式 `[A-Z]{2}[0-9]{8}` 所致)。**專案之正確樣式為 `^[A-Z0-9]{10}$`**(不變量 1),第二字元允許為數字(如 `A0` 開頭)。§1.1 之偵測**必須採用不變量 1 之樣式**,否則將漏檢合法代碼
- 116 個代碼經引擎逐一查詢,於主檔 **116/116 全部 `EXACT_MATCH`**;2.6.2 含 4 個、2.6.3 含 10 個
- **重組表格之實測失敗率(佐證 §1.1 禁令)**:以「名稱前半→代碼→名稱後半」假說重組並以主檔為標準答案比對,108 筆中 **100 筆相符、8 筆不符(約 7%)**;結構上代碼間距僅 84/108 為預期之 3 行。失敗樣態包含**跨列污染**——某代碼之重組名稱中混入另一代碼與另一藥品名稱,以及僅取得尾段碎片而完全不含藥品名稱者。此為 §1.1「不得由行序推斷對應」之實證依據,非臆測

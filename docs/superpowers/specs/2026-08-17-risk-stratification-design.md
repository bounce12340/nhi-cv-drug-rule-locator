# 風險分級與處方規定對照 — 設計

日期:2026-08-17 · 狀態:**已實作**(2026-08-18),與本文的差異記於文末

## 這是什麼

在現有的藥品查詢之外,加一個分頁:醫師逐題輸入病人的臨床條件,工具依 2026-09-01
公告附件二的判定條件算出 ASCVD 風險等級,並列出該等級的給付起始門檻、治療目標值、
處方規定步驟,以及主檔中對應的品項與價格。

參考對象是長庚藥師做的 CDSS(<https://cute-mermaid-133633.netlify.app/>)。實測該站
**不是 AI**:整份是一支 12,822 字元的 inline JavaScript,零 `fetch`、零 API 金鑰、零外部
script,風險分級是寫死的 if/else。本設計採同樣的「規則在瀏覽器裡跑」路線,但規則來自
受管資料集而非寫死。

## 不做什麼

- **不接 LLM。** 不需要 API 金鑰、不需要伺服器代理,病人資料不離開瀏覽器。
- **不給具體藥名與劑量的建議。** 給付規定只寫到「中至高強度 statin」,具體品項與劑量是
  醫師的判斷。畫面明講這件事。
- **不還原已移除的逐字條文分頁。** 只新增本設計所需的表一資料,不重建 2.6.1–2.6.3 全文。

## 對現有承諾的影響

現在畫面上寫「不判斷任何病人是否符合給付,**也不接受病人資料**」,`CLAUDE.md` 規則 5 亦然,
且有測試釘著。本功能收臨床數值,因此:

- 該句改為:不接受**可識別**病人資料(姓名、病歷號);臨床數值只留在瀏覽器記憶體,
  重新整理即消失,不寫 localStorage、不送出。
- `CLAUDE.md` 規則 5 同步改寫,`authored-copy.test.ts` 的斷言跟著改。

這是本設計唯一推翻既有承諾的地方,刻意寫在最前面。

## 資料層

新增受管資料集 `data/governed/nhi-lipid-risk-2026-09-01-r1/`,來源是**已在 repo 內**的
`data/governed/nhi-lipid-rules-2026-09-01-r1/attachment-2-rule-revision-table.pdf`
(SHA-256 `6389a5f654e0cb75…`,已驗證與 storage manifest 相符)。

用 `pdftotext -layout -enc UTF-8` 抽出的表一是欄位對齊的,可逐格轉錄。

> 注意:2026-08 移除的舊 `nhi-lipid-rules-structured` 資料集**不能拿來用**。它當初是逐單元
> 抽取、未用 `-layout`,表一被壓成單欄文字流,門檻數字與等級名稱錯行交錯(例:`LDL-C≧` 與
> `70mg/dL` 相隔數行,「非常高風險」黏著另一欄的「管風險」)。從那份推斷等級與門檻的對應,
> 與本專案已禁止的「從行序推斷藥名與代碼」是同一類錯誤。

| 檔案 | 內容 | 筆數 |
| --- | --- | --- |
| `risk-tiers.jsonl` | 6 個等級 × {起始門檻, 主要目標, 次要目標, 處方規定原文} | 6 |
| `tier-criteria.jsonl` | 各等級判定條件,含前提條件(見下) | 18 |
| `risk-factors.jsonl` | 6 項心血管風險因子;代謝症候群另含 5 項子條件 | 11 |

`scripts/risk-codegen.mjs` 比照現有兩支 codegen:寫死來源 PDF 的 SHA-256、各檔案雜湊、
預期筆數;任一項不符即以**離開碼 1** 中止,不產出。

數值一律照 PDF 原樣存字串:`LDL-C≧55mg/dL`、`non-HDL-C<85mg/dL`。不換算、不四捨五入。

### 判定條件是兩層的,不能攤平

原文的極高風險與非常高風險不是並列清單,而是「前提 **且** 下列任一」:

```
極高風險
 (一) 冠狀動脈疾病 且 任一:一年內心肌梗塞／≧兩次心梗病史／多支冠狀動脈阻塞／
                          急性冠心症合併糖尿病／周邊動脈疾病或頸動脈狹窄
 (二) 周邊動脈疾病 且 任一:冠狀動脈疾病／頸動脈狹窄
非常高風險
 (一) 經臨床檢查確診 ASCVD 且 任一(4 項)
 (二) 經影像確認 ≧50% 狹窄 且 任一(3 項)
```

只勾「一年內心肌梗塞」而未確認有冠狀動脈疾病,依原文**不成立**。因此
`tier-criteria.jsonl` 每列帶 `prerequisite` 與 `anyOf`,逐題流程先問前提、前提為否就整組略過。

高風險的 4 項則是並列(糖尿病／CKD／LDL-C≧190／CAC≧400),無前提。

## 規則引擎

`packages/domain/src/risk-stratification.ts`,純函式、無 I/O、回傳 frozen 值。

```
stratifyRisk(answers) → RiskAssessment
```

### 等級先後順序

順序取自 PDF 自身的編號(一、極高風險 二、非常高風險 三、高風險 四、中風險 五、低風險),
依序比對,命中即停:

1. 極高風險:任一組「前提且任一」成立
2. 否則 非常高風險:任一組「前提且任一」成立
3. 否則 高風險 4 條任一(含 **LDL-C≧190mg/dL**,故血脂值參與分級而非只用於門檻比較)
4. 否則數風險因子:≧2 → 中風險、1 → 低風險、0 → 0 項

因此「一年內心肌梗塞」+「0 項風險因子」不是衝突:該病人是極高風險,風險因子欄根本不會被查。

### 未知不等於否 — 本設計最重要的一條

風險因子中有兩項需要數值:`HDL-C(男<40／女<50)` 與 `代謝症候群(5 選 3)`。未填時該項是
**未知**,不是**不成立**。當成不成立會低估等級。

`stratifyRisk` 因此回傳兩種結果之一:

- `determined` — 等級 + `reason`(命中的那一條原文)
- `undetermined` — 可能的等級範圍 + **還缺哪幾項才能決定**

畫面的「下一題」就是從 `undetermined` 的缺項來的;已不可能改變結果的題目自動略過並說明原因。
這與現有「查不到就說查不到,不會替你猜」是同一個原則。

## 畫面

新增分頁「風險分級」,沿用現有 `app.css`,版面與藥品查詢一致(桌機左右兩欄、1024px 以下單欄)。

**左欄:逐題輸入**

- 已答題目收成一行,可按「修改」回頭改
- 只有當前題目展開
- 選項文字為判定條件**原文照列**
- 顯示「第 n / m 題」;m 隨已答內容縮短

**右欄:結果**

1. 等級大字卡 + 「依據:<命中的那一條>」
2. 四個數字:目前 LDL-C、給付起始門檻、主要目標、次要目標(non-HDL-C)。
   LDL-C 未填時該格顯示「未填」而非 0
3. 處方規定步驟卡(改寫自原文)+ 收合的「官方原文(未經改寫)」+ 出處與 SHA-256
4. 主檔中對應的品項與價格,沿用現有卡片;明講「工具不代為選取任何品項,強度分類與劑量請自行判斷」

品項分類以 `ingredient` 欄的**精確子字串**判定(含 `STATIN` 為 statin 類、含 `EZETIMIBE`
為 ezetimibe 類),**實作時必須實測筆數並寫進測試**,不得沿用本文件或草稿中的示意數字。
需一併確認主檔中沒有非降血脂但含 `STATIN` 字樣的成分(如 nystatin)。

步驟卡是改寫。原文完整存在資料集中,收合區塊可核對。

## 錯誤處理

- 未達可判定條件 → 顯示「尚無法判定」與缺項,**不猜**
- LDL-C 非數字或超出合理範圍 → 不接受,保留在欄位並說明
- 資料集版本不符 → 比照現有 lookup,回 `NOT_IN_VALIDATED_DATASET`
- 重新整理即清空;不寫入 localStorage

## 測試

domain 層:

- 6 個等級各自可達
- **前提不成立時整組不成立**:只勾「一年內心肌梗塞」但無冠狀動脈疾病 → 不得判為極高風險(負向測試)
- 先後順序:極高條件 + 0 項風險因子 → 極高(負向測試)
- LDL-C≧190 單獨成立即高風險
- 6 項風險因子計數;代謝症候群 5 選 3 的邊界(2 項不成立、3 項成立)
- **未知不得被當成否**:留白 HDL-C 且已知 1 項因子 → `undetermined`,而非低風險
- 每一個門檻與目標值逐格對 PDF
- frozen

app 層(`renderToStaticMarkup`):

- 結果卡永遠帶「依據」那一行
- 步驟卡的每一步都能對回原文
- 未判定時不顯示任何等級
- 免責語整頁仍只出現一次

## 實作順序

1. 轉錄三個 jsonl(含 `prerequisite`/`anyOf` 結構)+ `risk-codegen.mjs`(含 fail-closed 測試)
2. `risk-stratification.ts` + 測試
3. 分頁與逐題 UI + 渲染測試
4. 接上主檔品項清單
5. 改寫承諾文字、`CLAUDE.md`、README

## 實作後追記(2026-08-18)

實作時有六處與上文不同,都是動手後才量得到或看得出來的。上文保留原樣,差異寫在這裡。

**一、處方規定不是「改寫」,是照原文編號切開。** 上文第 126、134 行說步驟卡是改寫。實作時發現不必:
原文本身就是「一、二、三」的編號結構,直接依編號切成三張卡即可,一個字都不用改。渲染測試會把三張卡
的內容重新接起來,斷言與轉錄的段落逐字相同。改寫的風險沒有必要承擔。

**二、多了一欄「非藥物治療」不轉錄。** 上文的 schema 沒提到這欄。它確實在表一裡,但跨列合併,
`pdftotext` 只給碎片,拼回哪一列屬於哪個等級只能靠行序推斷——正是本設計要避免的那類錯誤。因此明文
不轉錄,並記在 `TRANSCRIPTION.md` 與來源登錄,不讓它看起來像遺漏。

**三、「0 項心血管風險因子」列沒有處方規定。** 上文假設六個等級都有處方規定原文。實際上處方規定欄
只有三個自帶標題的區塊(極高、非常高／高／中、低),沒有一個提到這一列。次要目標值同樣未列。兩者都
記為 `null`,畫面明講「公告未列」,不從上一列借。

**四、品項筆數與草稿的示意數字差很多。** 上文第 130 行要求實測,實測結果:含 statin **396**、
含 ezetimibe **27**、兩者皆含 **19**、兩者皆無 **203**。草稿畫面上的 186／37 是我編的,已作廢。
七個 statin 成分全部確認過,沒有 nystatin 之類的誤中。

**五、清單只涵蓋公告提到的一部分。** 這是實作時才發現的:處方規定另外點名 PCSK9 單株抗體、siRNA、
ATP citrate lyase 抑制劑,主檔**一筆都沒有**(evolocumab／alirocumab／inclisiran／bempedoic 全部 0 筆)。
不講的話,清單會被讀成「公告允許的全部」。畫面因此先講這句,再列品項。

**六、品項多了一層成分分組。** 上文只說「沿用現有卡片」。396 張卡一次攤開沒有人能用,所以先選成分
(atorvastatin 55、rosuvastatin 46…)再展開該成分的品項卡。分組名稱同樣取自成分欄的精確子字串。

另外兩件上文提過而實作時確認的:生理性別與年齡**沒有**做成獨立題目——風險因子二、三、四的原文自己
就寫明了男女各自的門檻,由醫師判斷比工具代算安全;LDL-C 沒填就無法排除高風險,這是 LDL-C≧190mg/dL
身為判定條件的直接後果,畫面會說明原因而不是默默卡住。

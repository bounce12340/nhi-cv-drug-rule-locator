# Phase 1 governed intake runbook(草案 v0.1,待 RA 核定)

本文件定義官方類資料(規則、支付價、公告附件)從「已收件、僅雜湊記錄、留置 repo 外」走到「已核准、已驗證、版本化入庫」的**治理程序**。它是 v3.2 §30 類規劃產物:純程序設計,**不含任何收件 payload,不解除 RDL-005**——每一次實際匯入仍需依本程序逐案取得 RA 核准。

## 0. 目的與邊界

- **Phase 1 的終點**:某一版本的官方類資料集,在 governed 儲存區內具備完整出處、通過驗證、取得 RA 逐案核准。**終點不包含**把資料接上 `@nhi-cv/domain`、API 或 UI——那是 Phase 2(versioned import pipeline)與 Phase 3(controlled release)的閘門,各有其審查。
- 在 Stage 4 核准之前,收件 payload 一律留在 repo 外,repo 只允許雜湊、筆數、位元組數與程序紀錄(RDL-007)。
- 本 runbook 生效不改變任何 BLOCKED 決策;RDL-005 的每一次「窄幅解除」都只針對單一資料集版本、單一用途,並須由 RA 記入決策日誌。

## 3. Stage 1|來源登錄與出處補全

**目標**:每一個收件檔案取得可稽核的出處紀錄,並由 RA 確認真實性。

1. RA(或其指定提供者)就**每一個**已收件檔案填寫來源登錄表,欄位:
   - 檔名與 SHA-256(必須與 docs/spec-source-status.md 收件紀錄一致)
   - 來源管道(官方網站網址/公文/紙本公告掃描,擇一並附可驗證參照)
   - 公告參照號與生效日期(以收件紀錄中已登載者為準)
   - 取得日期與取得方式;保管人(custodian)
   - 提供時的完整性聲明(是否節錄、是否轉檔、轉檔工具)
2. 派發方對照收件紀錄**重新計算雜湊**;不一致 → 該檔案退回,標記 `HASH_MISMATCH`,不得進入後續 Stage。
3. RA 對 v3.2 prompt 檔做真實性確認(readiness 缺口 #6):確認收件位元組即原始 v3.2。
4. 產出:`docs/source-register/`(每檔一筆登錄紀錄,metadata only)+ RA 簽記(語式見 §9)。

**失敗處置**:任一欄位缺漏 → 該檔案停在 `PROVENANCE_INCOMPLETE`,不阻擋其他檔案。

## 4. Stage 2|Intake 軟體能力建置(派工給建置者)

**目標**:把 `@nhi-cv/source-intake` 的隔離架構延伸出官方類通道。全部經派工單 + 驗收 + RA 簽核,預計 3–4 張派工單:

1. **Schema v2**:新增 `OFFICIAL_CANDIDATE` 分類(與 `SYNTHETIC_TEST_ONLY` 並存、不互通);來源參照允許官方管道型別;RA 證據結構沿用並強化(核准語式、核准範圍欄位)。
2. **Authority registry**:預設仍為空;RA 作為 authority 必須由呼叫端顯式注入,並綁定 RDL-009 紀錄參照。
3. **Governed 儲存設計**:核准後 payload 的存放位置與格式(版本化、含生效窗、來源參照);與 demo 資料嚴格分離,且**不得**被 domain/API/UI 引用(以測試鎖定)。
4. **負向測試**:雜湊不符、出處缺漏、未注入 authority、RA 證據缺漏/被拒、跨分類混用——一律 fail closed 且維持 `QUARANTINED`。
5. 核准前的任何 outcome,`publishable`/`downstreamUseAllowed` 恆為 `false`;核准後也僅轉為「可入 governed 儲存」,不等於可發布。

## 5. Stage 3|驗證與雙重覆核

**目標**:在不把 payload 寫進 repo 的前提下,產出可供 RA 判斷的驗證報告(統計與結論,metadata only)。

1. **結構驗證**:欄位數、列數對照宣告(§6 期望量);代碼欄逐筆通過與 domain 相同的正規化與表面格式檢查(10 碼、字元集),不合格逐筆列入報告(以列號引用,不引內容)。
2. **交叉一致性**:例外清單的代碼是否落在對應母集合;版本/日期欄是否在宣告生效窗內;跨檔案重複與衝突偵測。
3. **雙重覆核**:建置者產出驗證程式與報告 → 驗收方以獨立路徑重跑並比對;任何差異 → 差異報告,退回。
4. **邊界案例送裁**:凡規格書與 v3.2 條文對同一產品的分類有出入者,列入「解釋待決清單」送 RA(§9);**在 RA 裁決前,任何軟體不得編碼任一種讀法**。目前已知待決:一項複方產品的分類歸屬(收件紀錄中已標記,此處不具名)。

## 6. Stage 4|RA 核准與 RDL-005 窄幅解除

1. 派發方彙整提交:來源登錄 + 驗證報告 + 解釋裁決紀錄 + 擬核准範圍(哪些檔案、哪個資料集版本、何種用途)。
2. RA 逐案核准,固定語式:**`INTAKE-APPROVE <資料集版本> <manifest SHA 前 7 碼>`**;未綁定版本與雜湊的核准視為未完成。
3. 核准後由派發方在決策日誌新增一條 RDL(引用核准語式原文與範圍),明載:本次解除**僅**及於該版本、該用途;RDL-005 對其餘一切維持 BLOCKED。
4. 核准範圍變更、檔案重傳(雜湊改變)、生效日更動 → 原核准失效,回到 Stage 1 重走。

## 7. Stage 5|版本化入庫(Phase 1 終點)

1. 依核准範圍把 payload 放入 governed 儲存(Stage 2 設計的位置),附:資料集版本、生效窗、來源登錄參照、核准 RDL 編號、匯入雜湊(再驗一次)。
2. 入庫 PR 走完整六項 CI + 驗收 + RA `PASS <sha7>`;governance-scan 的排除清單屆時**由 RA 核定後**擴充至 governed 儲存路徑(在此之前任何 payload 入 repo 都會被紅線攔下——這是設計,不是障礙)。
3. 入庫完成 = Phase 1 對該資料集收尾。**交棒條件**(Phase 2 才能開始):入庫資料集存在、demo 資料未受影響、domain/API/UI 零引用(以測試證明)。

## 8. Stage 6|變更管理與再匯入

- 新公告 → 對新檔案重走 Stage 1–5;新版本**只能新增,不得覆寫**既有版本(供回溯查詢)。
- 版本汰換:新版本生效不刪舊版本;查詢語意(as-of-date 對應版本)屬 Phase 2 設計。
- 保存年限與汰除政策:RA 於首次入庫前核定(readiness 缺口 #8),記入決策日誌。
- 回滾:入庫後發現資料錯誤 → RA 簽記撤銷該版本核准(新 RDL),儲存區標記 `REVOKED`,不物理刪除。

## 9. 解釋程序(interpretation procedure)

補齊 readiness 缺口「RA-approved interpretation procedure」:

1. 任何人(含代理)發現條文/規格/資料間的歧義 → 開一筆「解釋待決」紀錄(問題、出處引用、可能讀法、影響範圍;不引 payload)。
2. 派發方彙整選項與利弊,以彈跳選項向 RA 提請裁決;RA 裁決語式:**`INTERPRET <待決編號>: <裁決摘要>`**。
3. 裁決記入決策日誌(或解釋紀錄檔)後,才允許任何軟體編碼該讀法;裁決前一律 fail closed / 標記待人工確認。
4. 裁決可被新公告推翻:新證據 → 重開待決 → 新裁決,舊裁決保留於歷史。

## 10. 紅線與失敗處置(全程有效)

- payload 在 Stage 4 核准前不入 repo;governance-scan 全程強制。
- 雜湊驗證失敗、出處缺漏、RA 證據缺漏 → 一律 fail closed,停在當前 Stage,不得「先做後補」。
- 部分資料不得推斷補齊(例:表二條文未到,適用表二的品項只能標示「條文待補」,不得引表一替代——此為 Phase 2 顯示層義務,於此預告)。
- 病人資料零容忍;任何檔案若含病人欄位 → 整檔拒收並通報 RA。
- 本 runbook 的任何修改屬治理變更:僅派發方可提交,RA `PASS <sha7>` 後生效。
